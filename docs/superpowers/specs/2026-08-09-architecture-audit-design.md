# 架构健康度全景审计设计(2026-08-09)

## Context

用户提供了一份关于架构腐朽(architectural decay)的判断文本,包含四大腐朽信号与三种典型表现,希望对照该标准对 pu-learning-toolbox 做一次全库全景审计,产物为仓库内审计报告(可持续复跑)。

- **审计范围**:全库(`pu_toolbox` 代码面 + `tests/benchmarks/scripts/examples` 工程面 + `docs/README` 文档面 + git 历史/CI/skills 治理面)
- **产物**:`docs/dev/architecture_audit.md`,逐信号绿/黄/红 + 证据 + 建议 + 行动项清单 + 复跑指南
- **边界**:纯审计,不改代码、不动文档、不引入新机制;red 项进 backlog 由用户决策;不触碰队友分支

## 判断框架(源自用户文本,操作化定义)

| 信号 | 审计操作化定义 |
|---|---|
| S1 删除风险 | 死代码/僵尸字段/无法安全移除的兼容层、无人引用的导出 |
| S2 局部性丧失 | 超大文件、依赖方向混乱、API 契约未被测试锁定的部分 |
| S3 承重 bug | 错误行为被下游依赖为契约;`api_only` 假实现;文档记录了错误行为 |
| S4 疤痕组织 | 只增不减的修补、僵尸分支/字段、掩盖性 workaround |
| T1 真相分裂 | 同一规则多份副本各自演化(双语 README、method card vs 实现、门禁范围) |
| T2 概念膨胀 | 无清理机制的新名词、别名泛滥、术语表缺失 |
| T3 治理腐朽 | 永远通过的检查、带 skip 标记的测试、价值度存疑的门禁 |

## 执行方式:领域分派子代理并行

| 代理 | 领域 | 重点对象 |
|---|---|---|
| A | 代码面 | `pu_toolbox/` 全部 .py:死代码、重复实现、大文件局部性、契约漂移 |
| B | 工程面 | `tests/` + `benchmarks/` + `scripts/` + `examples/`:测试有效性、skip 标记、门禁脚本健康 |
| C | 文档面 | `docs/` 40 篇 + README 双语:文档-实现漂移、双语漂移、过时引用 |
| D | 治理面 | git 历史 + CI + skills + 门禁体系:演化轨迹、门禁价值度、决策记录缺失 |

每个代理输出:按 4 信号 × 3 表现组织,**每项发现 = 信号名 + 绿/黄/红 + 证据(file:line)+ 置信度**。代理只读,不改任何文件。

## 报告大纲(docs/dev/architecture_audit.md)

1. 审计元信息(日期、范围、复跑方法)
2. 总评:健康度判词 + 代谢率/腐朽率评估
3. 四信号 × 三表现逐条:状态 + 证据 + 影响 + 建议
4. 行动项清单(按优先级排序,red 项必列)
5. 复跑指南(定期重跑,维持代谢率 > 腐朽率)

## 质量保障

- 所有发现必须带 `file:line` 证据;子代理置信度 < 高 的标注
- 主上下文对全部 red 项**亲自抽样复核**再写入报告,防误报
- 报告遵循现有 docs 风格,双语场景写明"中文为准"

## 验证方式

- 四代理并行产出结构化发现 → 主上下文汇总
- red 项抽样复核(亲自读代码确认)通过后才写入报告
- 报告提交后 `check_doc_links` 门禁通过(新报告链接合法)
