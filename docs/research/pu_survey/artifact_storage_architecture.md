# 实验制品存储架构（面向 8 数据集 × 22 方法）

状态日期：2026-09-30。状态：**架构设计**；阶段 1 的实施见
[`epoch_checkpoint_reclaim_plan.md`](epoch_checkpoint_reclaim_plan.md)，决策登记为 D25。

定位：本文回答「在满足实验要求的前提下，如何从软件层面避免 B4 式容量问题在放大后的实验规模上重演」。
它不是单点修复的方案书，而是制品模型的分级设计与迁移路径。

## 1. 触发与规模推演

B4（`nnpu`/`cifar10`/`native_cnn`，35 runs）的逐 epoch 全量快照约 280 GB，而 AutoDL 数据盘可用约 25 G、
文件存储默认上限 200 GB。这是一次**局部阻塞**，但推演到协议要求的规模就不是局部问题了：

| | 数据集 | 方法 | 估算 runs |
|---|---|---|---|
| 当前 P2.1 | 3 | 7（6 PU + oracle） | 645 |
| 协议 §2.1 / §4 要求 | **8**（IMDB、20News、CIFAR-10、ADNI、MNIST、F-MNIST、Spambase、Connect-4） | **22**（21 PU + oracle） | **~6000+** |

其中 4 个是图像数据集，都要走深度训练路径。沿用现有策略（深度 run 每 run 8–9 GB），
全量 checkpoint 会进入 **TB 量级** —— 这不是扩容能解决的：数据盘的容量上限、文件存储的 200 GB 默认上限、
跨平台传输成本、归档校验时间，任一项都拦得住。

**结论：这是架构问题，必须在制品模型层面解决，而不是继续加磁盘。**

## 2. 根因

根因不在「存得多」，而在**存错了东西**。

选择准则实际消费的输入，逐行核验如下：

| 准则 | 实现 | 消费的输入 |
|---|---|---|
| OA | `select_threshold(scores, labels, candidates)`（`strategies.py:236-248`） | 验证侧分数 + 标签 + 阈值网格 |
| PA | `proxy_accuracy(scores, labels, threshold, class_prior)`（`strategies.py:251-278`） | 验证侧分数 + PU 标签 + 阈值 + π |
| 二者共同的归一化 | `strategies.py:320-335` | 分数本身（min-max in val space） |

也就是说：**两个准则都是「验证侧分数 + 标签 + 先验」的函数，全程不接触模型权重。**
而 `ProtocolOA.select` 里模型唯一的作用是 `model.decision_function(x_val)` 产出那列分数
（`strategies.py:321`），取到分数之后模型再没被使用过。

可是当前持久化的是**模型权重**（`checkpoints.py:232-258` 每个 epoch 落一份 `.pt`），
而权重的长期用途只有两个：

1. **恢复模型做 test 评测** —— 这一步在 **run 内**完成（`runner.py:483-518`），不需要跨 run 持久化；
2. **事后模型级复核** —— 需要的是**被选中的那个** epoch 的权重，不是全部 epoch。

**全部 epoch 的权重从来没有被长期需要过**：`pilot_plan.py:807` 说 `Nothing deletes them`，
理由是「offline selection needs them afterwards」，但 selection 就发生在同一个 run 进程内。
于是「为可审计而全量留存」在放大规模后反噬了可审计本身 —— 存不下就无从审计。

## 3. 制品分级（目标架构）

| 级别 | 内容 | 每 run 量级（CIFAR-10 深度） | 留存策略 |
|---|---|---|---|
| **L1 决策记录** | 逐 epoch × 每准则的**验证侧分数向量**，附既有的 threshold / 指标 / π 来源 | **~4 MB** | 永久；进归档；审计与复现的**主依据** |
| **L2 选中权重** | PA 与 OA **各自选中**的 epoch 权重（weights-only） | **~90 MB** | 批次归档期内保留；跨批次去留由容量预算决定（§7、§9.3） |
| **L3 轨迹权重** | 全部候选 × 全部 epoch 的权重 | **~8–9 GB** | **仅 run 期间**存在，不入归档 |

现状是：L3 全量持久，L2 混在 L3 中（选中项只是其中一个文件），L1 只有**聚合后**的指标
（`validation_metrics`），没有可供重放的分数向量。目标架构把三者分开：**把 L3 的存储义务转移到 L1**。

L1 的分数向量必须按 val 侧逐个视图记录（`clean_val` 供 OA、`pu_val` 供 PA），
因为两套准则读的是不同的验证集。

### 3.1 L1 的最小充分集

只说「记录分数向量」**不足以**支撑 §4 承诺的逐位重放。两套准则的判据都是
`(分数, 标签, 阈值网格, π)` 的函数（`strategies.py:236-278`），因此 L1 必须一并锁定：

| 项 | 内容 | 依据 |
|---|---|---|
| 分数向量 | 逐 epoch × 每准则、**归一化后**的 val 侧分数，并附该视图的 affine 常量 | `strategies.py:326-335`（OA）、`:427-437`（PA） |
| **有序标签** | 与分数**逐位对齐**的验证标签向量，附可独立校验的来源引用（`split_ref` + 视图 + 样本顺序 + sha256） | 两个准则都消费 `labels`（`strategies.py:246`、`:273-278`） |
| 阈值网格 | 本次实际使用的候选集（默认 `np.linspace(0, 1, 11)`，可被覆盖） | `strategies.py:312-313`、`:409-410` |
| 并列规则 | 严格大于 → **保留最早**：候选序 → epoch 序 → 最低阈值 | `strategies.py:350`、`:458`、`:231-232` |
| π | 数值与其来源 | `strategies.py:398-406` 拒绝缺省 |
| 数值细节 | dtype，以及**归一化时点**（记录前做还是重放时做，二选一并写死） | `checkpoints.py:75-79` 的浮点边界先例 |

**归一化时点的现状**是「记录前、在 val 侧做」，affine 常量随后进入 test 评测路径
（`runner.py:497-507`）。阶段 2 若把分数落盘，必须沿用同一时点，否则重放的阈值语义会漂移。

**标签访问边界**：分数由选模层计算，标签也只在选模层消费。
OA 的 `clean_val` 真实标签与 PA 的 `pu_val` 标签**都不得经回调回流到训练器或标注机制** ——
那会把 oracle 信息泄漏进训练过程。现有的视图守卫
（`strategies.py:307-308`、`:393-394`）必须保持为唯一闸门。

## 4. 为什么 L1 足以支撑审计与复现

有 L1 之后，选择过程可以**逐位重放**：对每个 epoch 重算归一化、重跑阈值扫描或 proxy-accuracy 扫描，
验证「选中项确实是 argmax」。这正是协议 §5 要求的「选择 artifact 可复核」的实质内容，
而且比现状更强 —— 现状只记录了选中项的结果，重放需要把 GB 级权重全部恢复一遍。

**确实失去的能力**：用**新的**准则在旧轨迹上重选。但这条损失是可控的 ——

- 协议是**预注册**的，准则在跑批前冻结（`survey_execution_plan.md` §2），不存在「事后换准则」的合法场景；
- 若将来新增准则且它同样只依赖验证侧分数，L1 仍足以重放；
- 只有当新准则需要**重新前向**（不同输入变换、模型的其他输出）时 L1 才不够，那属于协议变更，
  应当随协议变更一起重新预注册并重跑，而不是靠翻旧权重。

## 5. 存储量推演

| 范围 | 现状（L3 全量） | 目标（L1 + L2） | 倍数 |
|---|---|---|---|
| 单个深度 run | ~8.5 GB | ~94 MB | ~90× |
| B4（35 runs） | ~280 GB | ~3 GB | ~90× |
| 当前 645 runs 的深度部分（~215） | ~1.8 TB | ~20 GB | ~90× |
| 未来 ~6000 runs 的深度部分（按 ~2000 估） | ~17 TB | ~190 GB | ~90× |

数字为**量级估算**（依据 `epoch_checkpoint_delivery.md:44-45` 的 44 MB/权重与实测 epoch 数），
正式规划须以 dry-run 输出为准。

**约 190 GB 不是可行性结论，也还不构成预算。** 它只是 L1 + L2 的裸量级，且已逼近文件存储的
200 GB 默认上限（§1），没有为下列项留余量：

- 日志（§7，含 B3a 已观测到的警告刷屏）；
- manifest 与 L1 的元数据开销；
- **归档打包时的并存副本** —— 打 tar 期间原件与包同时占用，峰值可达成品量的两倍；
- 多组件方法（Self-PU 双 teacher、Dist-PU 等）按组件数的倍数放大。

阶段 2 启动前须给出一张**按数据集 × 方法**的预算表，列明稳态占用、单 run 峰值与归档临时峰值，
并以该表而非本节的点估计回答「容量够不够」。

## 6. 迁移路径与不返工论证

| 阶段 | 内容 | 时机 | 对选模的影响 |
|---|---|---|---|
| **阶段 1** | 保留选中、回收其余（D25） | 本次，赶在 B3b 启动前 | **无**：只改「跑完后盘上留什么」 |
| **阶段 2** | L1 补全（逐 epoch 分数向量落盘）+ 选择改为可重放；L3 不再持久化 | P2.2 之后 | **执行结构变**：由「先训完再离线选」改为「逐 epoch 滚动选」；结果须证明等价 |
| **阶段 3**（可选） | L1 压缩、L2 按需降精度、归档直传远端 | 按需 | 无 |

### 6.1 阶段 1 与阶段 2 的关系（不是等价物）

阶段 1 交付的是「**选中权重 + 元数据**」，其中元数据只有聚合后的逐 epoch 指标，
**没有分数向量**（见 §3 开头）。阶段 2 才补齐 L1。因此：

- 阶段 1 是阶段 2 的**前置子集**，**不是终态的等价物**；
- 阶段 1 达成的口径是「选中权重可留存、阈值可复核」，**不能**宣称具备逐位重放能力。

**为什么阶段 1 仍不是白做**：

- 它**立刻**解除 B4 的容量阻塞，而阶段 2 要等到 P2.2 之后；
- 阶段 2 会把阶段 1 的回收逻辑转为**「全量持久化模式」**（调试、小规模、单 run 复核用），
  不是删除，该路径本身有独立价值；
- **接口已预留**：`EpochCheckpoint`（`checkpoints.py:82-110`）已是「引用 + 元数据 + 可恢复」的抽象，
  阶段 2 只需新增一个并列的「分数附件」类型，不必推翻现有结构。

### 6.2 阶段 2 的执行契约（本架构可行性所系）

**时序问题是阶段 2 的第一道坎。** 现有流程是全部候选训练完后，由
`ProtocolOA.select` / `ProtocolPA.select` **各自**遍历全部候选的全部 epoch、逐个 `restore()`
评分（`strategies.py:317-318`、`:416-417`，`checkpoints.py:123-132`），随后再 `restore()`
选中权重做 test（`runner.py:483-495`）。**选中项在选择完成前是未知的**，所以
「源头只落 L1 + L2」不可能靠事后挑拣实现。阶段 2 必须改为：

1. **逐 epoch 前向**：某 epoch 训练结束后立即在 val 侧出分数；
2. **立即落 L1**：写入该 epoch 的分数记录（§3.1 的全部字段），此后该 epoch 无须再由权重重算；
3. **滚动更新最优**：用分数更新该准则的当前最优，并列按 §3.1 的规则判定。
   **OA 与 PA 各维护一份**，因此一次遍历须同时喂两个准则 —— 否则要么两遍恢复，
   要么算完 OA 时 PA 需要的权重已经被丢弃；
4. **丢弃非最优权重**：该 epoch 若未刷新任一准则的当前最优，其权重**从不写盘**；
5. **收尾**：run 结束仅剩至多两份权重（OA 最优 + PA 最优，同一文件被两者选中时合并为一份），
   再做 test 评测。

**峰值**由「全部候选 × 全部 epoch」降为「当前最优 ≤2 份 + 在算的 1 份」，约 `3 × 90 MB`。

**等价性必须被证明，不能被假定**：滚动选择与离线全量选择结果相同，前提是准则只依赖
**单个 epoch 的分数**、且与遍历顺序无关 —— 这对当前两套准则成立（`strategies.py:350`、
`:458` 的最优比较只取单个 epoch 的标量值），但**须由测试证明**（同一轨迹下两条路径的
`SelectionArtifact` 与 `test_results` 逐值相同），不得仅凭本段论证合入。

**视图隔离**：分数在选模层计算，标签也只在选模层消费。实现时**不得**通过回调把
`clean_val`（或 PA 的 `pu_val` 标签）交给训练器或标注机制 —— 那会把 OA 的 oracle 信息
泄漏进训练过程。现有视图守卫（`strategies.py:307-308`、`:393-394`）必须保持为唯一闸门。

### 6.3 manifest 状态须扩为三态，不能沿用 reclaimed

阶段 1 的 `reclaimed` 语义是「**曾落盘、后回收**」，因此它保留原 `path` 与 `sha256`
（`epoch_checkpoint_reclaim_plan.md` §4）。阶段 2 中被丢弃的 epoch 权重**从未写盘**，
既无路径也无摘要：给它标 `reclaimed=true`、或补一个虚构路径，都是**伪造证据**。

阶段 2 须并列定义**第三种状态**（例如「未生成权重文件」），并规定：

- 三态互斥且穷尽：**从未写盘 / 曾写盘且已回收 / 仍在盘上**；
- 旧记录的兼容读法：缺该字段一律按「仍在盘上」解释（覆盖阶段 1 及之前的全量持久化 run）；
- 审计者据此区分「能力所限未生成」与「曾生成后被回收」。

### 6.4 阶段 2 的准入条件

以下未完成**不得开工**：

1. §3.1 的字段全部定稿，含 dtype 与归一化时点的二选一裁决；
2. §6.2 的滚动选择有**等价性测试设计**，视图隔离有明确落点；
3. §6.3 的三态语义登记；
4. §5 的按数据集 × 方法预算表；
5. **协议层决策登记**：把「完整快照可供 PA/OA 独立选择」（`epoch_checkpoint_delivery.md` §3）
   的判据从「权重在盘上」改为「分数在盘上且选择可重放」—— 与 D25 ③ 同性质的一次登记。

## 7. 其他存储维度（一并纳入）

容量问题不只在 checkpoint。按未来规模一并列出：

| 维度 | 现状 | 风险 | 处置方向 |
|---|---|---|---|
| **日志** | 每 run 一份完整 stdout/stderr；B3a 已被 sklearn `ConvergenceWarning` 刷屏（来源：`strategies.py:54` 的 `max_iter=100`） | 6000 runs 下可到百 GB 级，且淹没真实信号 | 警告去重与计数汇总、按 run 轮转、stdout 与归档日志分级 |
| **特征缓存** | `$ADAPTER_CACHE` 一次提取、多 run 复用，附 cache key 与摘要 | 良性，但仅覆盖 adapter 路径 | 推广为通用「表示缓存」（文本 SBERT、图像 backbone 特征），8 数据集下收益更大 |
| **数据集** | 3 个，含大文本与图像 | 8 个数据集含 ADNI（3D 医学图像），体量未测 | 提前测量；数据与制品分盘；只读挂载 |
| **manifest 体积** | `candidate_runs[].epoch_checkpoints` 内含逐 epoch 元数据 | 逐 epoch 分数若进 JSON 会显著膨胀 | L1 落为**独立二进制文件**（npz）+ manifest 只存引用与 sha256，与 checkpoint 同构 |
| **归档生命周期** | 每批一个 tar + sha256 | 规模放大后归档本身成为负担 | 按分级设定留存：L1 永久；L2 见 §3 与 §9.3；L3 不留。打包期间的并存副本须计入峰值（§5） |

## 8. 非目标（YAGNI）

以下不在本架构内，除非出现具体需求：

- 分布式训练与跨节点 checkpoint 共享；
- 在线/增量训练（当前 checkpoint 是推理快照，明确不支持 optimizer 续训，见 `checkpoints.py:7`）；
- 跨平台 checkpoint 迁移；
- 多机并发调度。

## 9. 未决事项

阶段 2 的准入条件已集中列于 §6.4，此处只记尚未定稿的内容。

1. **L1 的数值格式裁决**：float32 是否足够（阈值边界对浮点敏感，`checkpoints.py:75-79` 已有先例教训）；
   归一化在记录时做还是重放时做。两者必须择一并写死（§6.4 第 1 项）。
2. **22 个方法中的未接入者**：是否有非常规选模需求（例如需要模型内部状态、或多输出），
   须在接入时逐个确认；若有，不得默认其适配 L1 架构，**也不得默认 §6.2 的滚动选择对它成立**。
3. **L2 的核算与跨批次留存**：当前估算基于 ResNet-18 单组件；Self-PU 双 teacher、以及未来 22 方法中的
   多组件方法（Dist-PU 等）需按组件数重新核算。**跨批次保留期须与 §5 的预算表一并定稿** ——
   L2 一经删除，该 run 的模型级复核不可再恢复（训练的非确定性使「重跑即得同一权重」不成立），
   因此这是由预算驱动、有代价的决策，不得默认「永久」。
4. **L1 的落盘位置与形状**：每 run 一个 npz、还是按批次合并；须与 manifest 的引用方式一并定稿。
