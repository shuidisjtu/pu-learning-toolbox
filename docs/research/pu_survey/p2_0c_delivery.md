# P2.0c 交付：外部对照预注册

状态：工程交付完成。54 个锚点与 194 条映射已由 shuidisjtu 自审置为 accepted；
`review_status` 仍为 `pending_collaborator_review`，合作者独立复核未开始，复核记录见 [复核包](p2_0c_review.md)。
本交付**不产生实验结果**，也不证明任何算法复现成功——它冻结的是结果出来之后如何进行正确性审计。
上游要求见 [执行计划](survey_execution_plan.md) P2.0c；对照矩阵的机器可读真相源是
`pu_toolbox/experiment/survey_comparison_v1.json`，本文件解释其中的判读与边界，不另行维护一份参数表。

## 1. 交付物与程序权威

- `pu_toolbox/experiment/survey_comparison_v1.json`：来源、锚点、结果单元映射、矛盾记录、判定规则。
- `pu_toolbox/experiment/survey_comparison.py`：loader / digest / resolver / 覆盖校验 / 数值裁决 / 聚合报告。
- `tests/unit/experiment/` 下三个测试文件：载入与裁决、覆盖、报告契约。

**为什么是第二真相源而不是扩展执行协议。** 执行协议回答“要跑什么”，本矩阵回答“跑出来的数能与谁比、怎么比”。
两者变更节奏与签署主体都不同：把锚点登记进执行协议，会让一次锚点转录修正也触发协议版本升级，
并使执行侧的本机验证与文献侧的复核互相阻塞。两文件各自摘要、由 `bound_survey_protocol` 单向绑定——
执行协议不必知道对照矩阵的存在。

绑定方向是单向的：comparison 记录它绑定的 survey 摘要，survey 不记录 comparison。
因此签署时两者的改动必须原子落地，否则会出现指向旧摘要的悬挂引用（签署顺序见 §6）。

## 2. 对照矩阵的构成

### 2.1 资格是闭集，不是自由文本

六类 `eligibility` 构成精确集合，多一类或少一类都拒收。这条约束的目的是：**不允许在结果出来之后，
用自由文本临时决定某个单元是否参与裁决**。判定必须落在结果之前就写好的分类上。

`blocked_pending_pa_criterion` 单列，是因为 PA 选模准则尚未由合作者锁定（见执行计划的 R9）。
在此之前任何 PA 单元都不得做数值裁决，且该状态不能因为其他项通过而被顺手删除。

### 2.2 覆盖由协议推导

结果单元集合由执行协议程序化展开，不手工罗列——手工列表会在协议版本变动时静默过期。
校验器拒收四类致命情况：单元无映射、单元被映射两次、映射覆盖不到任何单元、锚点被多个映射复用。

第三类需要单独说明：**打错一个 c token 会同时造成一个真实单元漏项和一个幽灵映射**，
只查“单元是否都有映射”抓不到它，必须从两个方向同时校验。

### 2.3 行级映射：不发明坐标

三类来源里只有 PU-Bench 有标签频率轴，且只有一档；另两个 benchmark 与四篇原论文用的是固定正例率或真值类先验。
这类锚点**不硬塞进某个 c 档**：那会造成“某一档有锚点、其余各档没有”的假象，读者会误以为缺档意味着更弱或更强的对照。
改用行级映射（`scope="row"`），轴差异在行级显式声明，单元不声称存在它并不具备的对照。

## 3. 与外部来源的口径差异

本交付的核心不是转录音数，而是逐条判读“论文怎么写、代码怎么做、以哪个为准”。四条差异记入 `contradictions`，
一律 `resolution=code`，并强制其受影响锚点 `protocol_provenance=uncertain`——该状态**禁止进入数值裁决**。

**以代码为准的理由**：两个 benchmark 的仓库在论文发表后仍在演进，而生成论文表格的那段代码，
才是“表里印出来的那个数到底是什么”的一手依据；论文正文描述的是作者意图，意图与产物不一致时以产物为准。
这个选择的适用边界写在 `contradictions` 里：它记录的是**当时锁定的那个 commit**，不是“论文错了”的永久结论。

四处差异中，两处会改变后续计算：

- **误差棒的类型**。某个 benchmark 的题注写的是标准差，但生成表格的代码算的是标准误。这不只是命名问题：
  池化标准误的公式按两者分别实现，若把标准误当标准差再除一次样本量，会重复折算一次样本量因子，
  使判定阈值系统性偏严。因此 `uncertainty_kind` 是必填字段而非注释。
- **选模准则**。另一个 benchmark 的正文与附录说按验证 macro-F1 选 checkpoint，发布代码统一用另一套代理指标。
  无法判定已发表的表格出自哪一套，因此该来源的全部锚点登记为 `protocol_provenance=uncertain`。

另外两处分别影响 backbone 身份与预处理口径（后者决定了某些锚点是在归一化特征上产出的）。
它们的共同后果是：**两个 benchmark 来源的锚点全部不可参与数值裁决**，这是 v1 中 `numeric` 数量为 0 的主要原因之一。

`numeric=0` 是诚实的结果，不是缺陷：没有任何来源能同时在数据集、方法、标签频率、选模协议与训练路径上与我们对齐。
预注册规则本就允许这一结果，不为“有硬锚点”而放宽一致性条件。

### 3.1 数值产出方与论文出处分离

`value_producer` 与 `source_id` 是两个字段，因为“这个数谁算的”和“这个数从哪篇论文读到的”可以不同：
有论文报告的基线行，实际是作者用他人的官方代码库复现出来的。登记时若只看 `source_id`，
会让后来者把这行当成原论文数值去对照，而两者的协议条件并不相同。

该字段只做枚举校验，不参与任何判定——它服务于审计可读性，不改变裁决结果。

## 4. 判定规则

- **单位契约**：锚点以百分点存储，运行结果以 fraction 输入，转换在校验层完成并检查范围。
  指标不限于 accuracy：来源给的是 error rate 时，必须带显式转换规则，不得静默当作 accuracy。
- **池化标准误**：按锚点的 `uncertainty_kind` 分支计算——给标准差的按样本量折算，给标准误的直接使用。
  阈值取一个下限与池化标准误倍数的较大者，避免小样本下阈值退化为零。
- **三档结论**：数值裁决只允许三档结论，且只有“无法解释的偏差”升级为警报。
  另两档（实现错误、协议差异已解释）必须留下证据才能记录，避免用一句“协议不同”把偏差归档了事。

## 5. 与下游的接口

- **运行 manifest**：只写入 comparison 版本、摘要与解析出的 mapping id。
  跨 seed 聚合与文献裁决不属于跑批阶段，不在 manifest 里做。
- **聚合报告**：注解层**不写回测量层**。报告承载我方指标、锚点值、差值与判定，但原始结果与排名不受其影响——
  对照矩阵不能反向修改被测对象。
- **根因记录**：只在报告处于“待排查”状态时接受记录，且证据不可为空。
