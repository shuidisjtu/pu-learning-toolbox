# 实验制品存储架构（面向 8 数据集 × 22 方法）

状态日期：2026-09-30。状态：**架构设计**；阶段 1 的实施见
[`epoch_checkpoint_reclaim_plan.md`](epoch_checkpoint_reclaim_plan.md)，决策登记为 D25。

定位：本文回答「在满足实验要求的前提下，如何从软件层面避免 B4 式容量问题在放大后的实验规模上重演」。
它不是单点修复的方案书，而是制品模型的分级设计与迁移路径。

## 1. 触发与规模推演

B4（`nnpu`/`cifar10`/`native_cnn`，35 runs）的逐 epoch 全量快照约 280 GB，而 AutoDL 数据盘可用约 25 G、
文件存储默认上限 200 GB。这是一次**局部阻塞**，但推演到协议要求的规模就不是局部问题了：

| | 数据集 | 方法 | 估算 runs |
|---|---|---|---|
| 当前 P2.1 | 3 | 7（6 PU + oracle） | 645 |
| 协议 §2.1 / §4 要求 | **8**（IMDB、20News、CIFAR-10、ADNI、MNIST、F-MNIST、Spambase、Connect-4） | **22**（21 PU + oracle） | **~6000+** |

其中 4 个是图像数据集，都要走深度训练路径。沿用现有策略（深度 run 每 run 8–9 GB），
全量 checkpoint 会进入 **TB 量级** —— 这不是扩容能解决的：数据盘的容量上限、文件存储的 200 GB 默认上限、
跨平台传输成本、归档校验时间，任一项都拦得住。

**结论：这是架构问题，必须在制品模型层面解决，而不是继续加磁盘。**

## 2. 根因

根因不在「存得多」，而在**存错了东西**。

选择准则实际消费的输入，逐行核验如下：

| 准则 | 实现 | 消费的输入 |
|---|---|---|
| OA | `select_threshold(scores, labels, candidates)`（`strategies.py:236-248`） | 验证侧分数 + 标签 + 阈值网格 |
| PA | `proxy_accuracy(scores, labels, threshold, class_prior)`（`strategies.py:251-278`） | 验证侧分数 + PU 标签 + 阈值 + π |
| 二者共同的归一化 | `strategies.py:320-335` | 分数本身（min-max in val space） |

也就是说：**两个准则都是「验证侧分数 + 标签 + 先验」的函数，全程不接触模型权重。**
而 `ProtocolOA.select` 里模型唯一的作用是 `model.decision_function(x_val)` 产出那列分数
（`strategies.py:321`），取到分数之后模型再没被使用过。

可是当前持久化的是**模型权重**（`checkpoints.py:232-258` 每个 epoch 落一份 `.pt`），
而权重的长期用途只有两个：

1. **恢复模型做 test 评测** —— 这一步在 **run 内**完成（`runner.py:483-518`），不需要跨 run 持久化；
2. **事后模型级复核** —— 需要的是**被选中的那个** epoch 的权重，不是全部 epoch。

**全部 epoch 的权重从来没有被长期需要过**：`pilot_plan.py:807` 说 `Nothing deletes them`，
理由是「offline selection needs them afterwards」，但 selection 就发生在同一个 run 进程内。
于是「为可审计而全量留存」在放大规模后反噬了可审计本身 —— 存不下就无从审计。

## 3. 制品分级（目标架构）

| 级别 | 内容 | 每 run 量级（CIFAR-10 深度） | 留存策略 |
|---|---|---|---|
| **L1 决策记录** | 逐 epoch × 每准则的验证侧分数向量（**归一化后 + affine 常量**）、**有序标签**、阈值网格、π 来源 —— 完整字段见 §3.1 | **~16 MB** | 永久；进归档；审计与复现的**主依据** |
| **L2 选中权重** | PA 与 OA **各自选中**的 epoch 权重（weights-only） | **~90 MB** | 批次归档期内保留；跨批次去留由容量预算决定（§7、§9.2） |
| **L3 轨迹权重** | 全部候选 × 全部 epoch 的权重 | **~8–9 GB** | **仅 run 期间**存在，不入归档 |

现状是：L3 全量持久，L2 混在 L3 中（选中项只是其中一个文件），L1 只有**聚合后**的指标
（`validation_metrics`），没有可供重放的分数向量。目标架构把三者分开：**把 L3 的存储义务转移到 L1**。

L1 的分数向量必须按 val 侧逐个视图记录（`clean_val` 供 OA、`pu_val` 供 PA），
因为两套准则读的是不同的验证集 —— 视图集合由**该单元实际启用的协议**决定，不是恒为两个（见 §6.2）。

### 3.1 L1 的最小充分集

只说「记录分数向量」**不足以**支撑 §4 承诺的逐位重放。两套准则的判据都是
`(分数, 标签, 阈值网格, π)` 的函数（`strategies.py:236-278`），因此 L1 必须一并锁定：

| 项 | 内容 | 依据 |
|---|---|---|
| 分数向量 | 逐 epoch × 每准则的 val 侧分数，按 **`normalization_mode`** 记录（见下），并附 affine 常量 | `strategies.py:326-335`（OA）、`:427-437`（PA） |
| **有序标签** | 与分数**逐位对齐**的验证标签向量，附可独立校验的来源引用（`split_ref` + 视图 + 样本顺序 + sha256） | 两个准则都消费 `labels`（`strategies.py:246`、`:273-278`） |
| 阈值网格 | 本次实际使用的候选集（默认 `np.linspace(0, 1, 11)`，可被覆盖），**按出现序**参与比较 | `strategies.py:312-313`、`:409-410` |
| 顺序与并列 | 严格大于才更新 ⇒ **并列保留先遇到的**；完整比较顺序见下 | `strategies.py:350`、`:458`、`:231-232` |
| π | 数值与其来源 | `strategies.py:398-406` 拒绝缺省 |
| 数值细节 | 计算精度**保持现状**、存储精度 **float64** —— 两者不同，见下 | `checkpoints.py:45-62`（深度路径分数为 float32） |

**并列的比较顺序（必须固定，两条路径逐项一致）**：

1. **候选序** —— `trajectories` 列表序（`strategies.py:317`、`:416`）；
2. **轨迹内序** —— `trajectory.checkpoints` 的**列表序**（`checkpoints.py:126-130`）。
   该列表含 **epoch 与 component 两个维度**：Self-PU 在同一 epoch 产出
   `teacher_1` / `teacher_2` 两个 checkpoint（`checkpoints.py:211-216`、`:232-235`），
   因此「同一 epoch」不足以定位一个文件，component 必须在序内；
3. **阈值候选序** —— `threshold_candidates` 的**出现序**。
   `_best_threshold` 只在严格大于时更新（`strategies.py:231-232`），保留的是
   **首个最优候选**；`select_threshold` docstring 所称的 "lowest threshold"
   **只在候选网格非降序时成立**，自定义网格不得按「最低」理解。

**归一化契约（定稿）**

L1 保存**归一化后**的分数，重放**直接扫描阈值网格**，不重算归一化 —— 这与 test 评测路径的
既有语义一致（`runner.py:497-507` 复用同一组 affine 常量）。但「归一化后」有一个必须显式
建模的例外：**常数分数**。

| `normalization_mode` | 触发 | 存储内容 | 阈值语义 |
|---|---|---|---|
| `minmax` | `np.ptp(scores) > 0` | 归一化后分数 + `val_score_min` / `val_score_scale` | 阈值作用在归一化空间 |
| `constant_raw` | `np.ptp(scores) == 0` | **未归一化的常数分数**；两个 affine 字段为 `null` | 阈值直接作用在原始分数 |

依据：`strategies.py:329-335`（OA）、`:430-437`（PA）在 `scale == 0` 时**不归一化**、把 affine
记为 `(None, None)`，而阈值网格仍照常扫描原始分数。因此：

- 重放器必须靠 `normalization_mode` 区分两种模式，**不得**靠 affine 是否为空去猜；
- `val_score_min` / `val_score_scale` 为 `null` **只允许**出现在 `constant_raw`；
- 缺该字段，「逐位重放」对常数分数轨迹不成立。

**计算精度与存储精度是两件事**：

- **计算**沿用现状：`decision_function` 的返回 dtype、`np.ptp` / min-max / 阈值比较的算术
  一律不动。深度路径的分数是 **float32**（`checkpoints.py:45-62`：输入转 float32、输出
  `.cpu().numpy()` 不升精度），sklearn 路径是 float64。**若阶段 2 把计算统一升为 float64，
  那是选择语义变更，不能再声称与现状等价。**
- **存储**用 **float64**，只作用于归一化结果的落盘。float32 → float64 是**无损扩宽**，
  不改变已算出的值，仅避免存-取往返再引入误差。

**不声称「信息不丢失」**：`orig = norm * scale + min` 在有限精度下并不严格可逆
（`(x-a)/b*b+a ≠ x`）。L1 的目标是**重放已登记的归一化选择语义**，不需要反推原始分数。

**数值等价的验收方式**：同一轨迹下，由 L1 重放得到的
`(run_index, checkpoint_index, epoch, threshold)` 与**现行离线选择**严格相等（`==`，不是近似），
`metrics` 逐字段相同。测试须覆盖**并列**、**未排序网格**与**常数分数**三种边界。

**标签访问边界**：分数由选模层计算，标签也只在选模层消费。
OA 的 `clean_val` 真实标签与 PA 的 `pu_val` 标签**都不得经回调回流到训练器或标注机制** ——
那会把 oracle 信息泄漏进训练过程。现有的视图守卫
（`strategies.py:307-308`、`:393-394`）必须保持为唯一闸门。

## 4. 为什么 L1 足以支撑审计与复现

有 L1 之后，选择过程可以**逐位重放**：对每个 epoch 用已存的归一化分数重跑阈值扫描或
proxy-accuracy 扫描（**不重算归一化**，见 §3.1），验证「选中项确实是 argmax」。
这正是协议 §5 要求的「选择 artifact 可复核」的实质内容，而且比现状更强 ——
现状只记录了选中项的结果，重放需要把 GB 级权重全部恢复一遍。

**确实失去的能力**：用**新的**准则在旧轨迹上重选。但这条损失是可控的 ——

- 协议是**预注册**的，准则在跑批前冻结（`pu_survey_protocol.md` 的预注册规则），不存在「事后换准则」的合法场景；
- 若将来新增准则且它同样只依赖验证侧分数，L1 仍足以重放；
- 只有当新准则需要**重新前向**（不同输入变换、模型的其他输出）时 L1 才不够，那属于协议变更，
  应当随协议变更一起重新预注册并重跑，而不是靠翻旧权重。

## 5. 存储量推演

| 范围 | 现状（L3 全量） | 目标（L1 + L2） | 倍数 |
|---|---|---|---|
| 单个深度 run | ~8.5 GB | ~106 MB | ~80× |
| B4（35 runs） | ~280 GB | ~3.7 GB | ~80× |
| 当前 645 runs 的深度部分（~215） | ~1.8 TB | ~23 GB | ~80× |
| 未来 ~6000 runs 的深度部分（按 ~2000 估） | ~17 TB | ~212 GB | ~80× |

L1 一项按 §3.1 的定稿口径重算（float64 × `clean_val`/`pu_val` 两视图，约 16 MB），
较初版估算上调；L2 仍是 ~90 MB（ResNet-18 单组件）。量级结论不变。
两视图是 OA + PA 均启用时的**上界**，OA-only 单元（如 PN oracle）的 L1 更小。

数字为**量级估算**（依据 `epoch_checkpoint_delivery.md:44-45` 的 44 MB/权重与实测 epoch 数），
正式规划须以 dry-run 输出为准。

**约 212 GB 不是可行性结论，也还不构成预算 —— 它已经超出**文件存储的 200 GB 默认上限（§1）。
而这只是 L1 + L2 的裸量级，还没为下列任何一项留余量：

- 日志（§7，含 B3a 已观测到的警告刷屏）；
- manifest 与 L1 的元数据开销；
- **归档打包时的并存副本** —— 打 tar 期间原件与包同时占用，峰值可达成品量的两倍；
- 多组件方法（Self-PU 双 teacher、Dist-PU 等）按组件数的倍数放大。

阶段 2 启动前须给出一张**按数据集 × 方法**的预算表，列明稳态占用、单 run 峰值与归档临时峰值，
并以该表而非本节的点估计回答「容量够不够」。

## 6. 迁移路径与不返工论证

| 阶段 | 内容 | 时机 | 对选模的影响 |
|---|---|---|---|
| **阶段 1** | 保留选中、回收其余（D25） | 本次，赶在 B3b 启动前 | **无**：只改「跑完后盘上留什么」 |
| **阶段 2** | L1 补全（逐 epoch 分数向量落盘）+ 选择改为可重放；L3 不再持久化 | P2.2 之后 | **执行结构变**：由「先训完再离线选」改为「逐 epoch 滚动选」；结果须证明等价 |
| **阶段 3**（可选） | L1 压缩、L2 按需降精度、归档直传远端 | 按需 | 无 |

### 6.1 阶段 1 与阶段 2 的关系（不是等价物）

阶段 1 交付的是「**选中权重 + 元数据**」，其中元数据只有聚合后的逐 epoch 指标，
**没有分数向量**（见 §3 开头）。阶段 2 才补齐 L1。因此：

- 阶段 1 是阶段 2 的**前置子集**，**不是终态的等价物**；
- 阶段 1 达成的口径是「选中权重可留存、阈值可复核」，**不能**宣称具备逐位重放能力。

**为什么阶段 1 仍不是白做**：

- 它**立刻**解除 B4 的容量阻塞，而阶段 2 要等到 P2.2 之后；
- 阶段 2 会把阶段 1 的回收逻辑转为**「全量持久化模式」**（调试、小规模、单 run 复核用），
  不是删除，该路径本身有独立价值；
- **抽象可复用，但改动面不止「新增一个类型」**：`EpochCheckpoint`（`checkpoints.py:82-110`）
  的**必填字段就是权重路径与 `sha256`**，而 `selection_models`（`checkpoints.py:123-132`）
  的契约是「逐个恢复权重」。阶段 2 至少还要改三处输入契约：
  **轨迹**（不再持有全部 epoch 的权重引用）、**选模**（改为消费分数记录与滚动最优，
  而非恢复权重）、**manifest**（§6.3 的四态）。复用抽象不等于复用契约。

### 6.2 阶段 2 的执行契约（本架构可行性所系）

**时序问题是阶段 2 的第一道坎。** 现有流程是全部候选训练完后，由
`ProtocolOA.select` / `ProtocolPA.select` **各自**遍历全部候选的全部 epoch、逐个 `restore()`
评分（`strategies.py:317-318`、`:416-417`，`checkpoints.py:123-132`），随后再 `restore()`
选中权重做 test（`runner.py:483-495`）。**选中项在选择完成前是未知的**，所以
「源头只落 L1 + L2」不可能靠事后挑拣实现。阶段 2 必须改为：

1. **逐 epoch 前向**：某 epoch 训练结束后立即在 val 侧出分数；
2. **立即落 L1**：写入该 epoch 的分数记录（§3.1 的全部字段），此后该 epoch 无须再由权重重算；
3. **滚动更新最优**：用分数更新各准则的当前最优，并列按 §3.1 的规则判定。维护的是
   **本次单元实际启用的协议集**，不是固定的「OA + PA」两份；一次遍历须同时喂所有启用协议
   （否则要么多遍恢复，要么算完前一个时后一个要的权重已被丢弃）。
4. **丢弃非最优权重**：该 epoch 若未刷新任一**启用**协议的当前最优，其权重**从不写盘**；
5. **收尾**：run 结束仅剩至多 `启用协议数 × 选中组件数` 份权重（同一文件被多个协议选中时
   合并为一份），再做 test 评测。

**「协议集」是配置驱动的，不能写死成 PA + OA。** `runner.py:458-466` 遍历的是
`self.protocols`，而协议对启用条件有明确规定：

- **SAR 压力测试**：PA **仅作为诊断日志**，正式模型选择与结论只用 OA（`pu_survey_protocol.md:97`）；
- **PN oracle**：只以 `clean_val` 真实 Accuracy 选模，表中标为 `PN oracle (OA only)`，
  **不得伪造 PA 结果**（`pu_survey_protocol.md:159-161`）；
- **PA-ineligible 方法**：无法移除真实验证标签依赖者只进 OA / 补充表（`pu_survey_protocol.md:109-110`）。

因此阶段 2 对每个单元应「**按其实际启用且有资格的协议**分别维护滚动最优与 L1 记录」：
PN oracle 单元只产出 OA 的 L1 与 OA 选中权重，其余协议既不记录也不补造。
L1 的视图集合同样由启用协议决定（OA → `clean_val`；PA → `pu_val`），不是恒为两个视图。

**峰值**由「全部候选 × 全部 epoch」降为「各启用协议的当前最优 + 在算的 1 份」：
单组件口径下约 `3 × 90 MB`，多组件方法按组件数放大（§9.2）。

**等价性必须被证明，而且它不靠「顺序无关」成立。** 各准则都只在**严格大于**时更新最优
（`strategies.py:350`、`:458`），因此**并列时保留先遇到的项** —— 遍历顺序**有语义**，
不是无关变量。滚动选择要复现离线结果，必须与 §3.1 的完整比较顺序逐项一致：

- **候选序**：两处都按 `trajectories` 列表序（`strategies.py:317`、`:416`）；
- **轨迹内序**：离线按 `trajectory.checkpoints` 列表序（`checkpoints.py:126-130`，
  含 epoch 与 component 两个维度 —— Self-PU 双 teacher 即同 epoch 多 component），
  滚动须按相同次序产出；
- **阈值候选序**：按 `threshold_candidates` 出现序，未排序网格下保留首个最优候选。

**须由测试证明**：同一轨迹下两条路径的 `SelectionArtifact` 与 `test_results` 逐值相同，
且覆盖**并列**、**未排序网格**与**常数分数**三种边界。不得仅凭本段论证合入。

**执行调度顺序也必须锁定**（上面只说明了「顺序有语义」，还不够）。候选若并发训练、按
wall-clock 完成时间合并结果，候选序就会与离线流程不同。阶段 2 须二选一：

1. 候选**严格按 `trajectories` 顺序串行**执行；或
2. 允许并发，但结果按**预注册的 `candidate_index` 顺序**合并，**不得**按完成时间合并。

未择一之前，「候选序固定」只是逻辑描述，无法保证与离线选择一致。

**视图隔离**：分数在选模层计算，标签也只在选模层消费。实现时**不得**通过回调把
`clean_val`（或 PA 的 `pu_val` 标签）交给训练器或标注机制 —— 那会把 OA 的 oracle 信息
泄漏进训练过程。现有视图守卫（`strategies.py:307-308`、`:393-394`）必须保持为唯一闸门。

### 6.3 manifest 状态须扩为四态（并修正旧记录映射）

阶段 1 的 `reclaimed` 语义是「**曾落盘、后回收**」，因此保留原 `path` 与 `sha256`
（`epoch_checkpoint_reclaim_plan.md` §4）。阶段 2 中被丢弃的 epoch 权重则**从未调用
`torch.save`**，既无路径也无摘要：给它标 `reclaimed=true`、或补一个虚构路径，都是**伪造证据**。

但**三态也不够** —— 旧的**临时目录** checkpoint 会落在缝里。`checkpoint_dir=None` 时
`EpochCheckpointTrainer` 走 `tempfile.TemporaryDirectory()`，**同样执行 `torch.save`**
（`checkpoints.py:191-198`、`:245`），只是 `persistent=False` 让 `reference()` 把 `path`
序列化为 `null`（`checkpoints.py:103`、`:256`），run 结束后由临时目录生命周期清理。
所以 `persistent=false` / `path=null` **只证明「没有可持久定位的路径」，不证明「从未写盘」** ——
`epoch_checkpoint_delivery.md:38-39` 的措辞正是「不能据此宣称可持久复现」，而不是「未写过」。

阶段 2 须定义**四态**：

| 状态 | 含义 | 盘上现状 |
|---|---|---|
| `retained` | 已持久化，路径与摘要可复核 | 在 |
| `generated_reclaimed` | 曾持久化，后被阶段 1 回收（保留原 `path` / `sha256`） | 不在 |
| `generated_ephemeral` | 曾写入**临时目录**，未持久留存 | 不在 |
| `not_generated` | **从未调用 `torch.save`**（阶段 2 新引入） | 不在 |

旧记录的兼容读法（**按旧字段逐条映射，不得一律归为任一态**）：

1. `reclaimed=true` → `generated_reclaimed`；
2. `persistent=false` 或 `path=null` → **`generated_ephemeral`**（**不是** `not_generated`）；
3. 其余（`persistent=true` 且有 `path`）→ `retained`。

`not_generated` 只由阶段 2 的新写入路径产生；**历史 manifest 中不存在该态**，
把旧的临时记录归入它等于改写历史。

区分 `generated_ephemeral` 与 `not_generated` 的审计意义：前者说明该 epoch **确实产出过权重**
（只是未留存），后者说明**根本没有产出**。两者对「这次训练是否正常完成」的证词不同。

**「记录为在盘」≠「文件确实在盘」**：manifest 承载的是**记录状态**，实际存在性须由校验动作
确认（`EpochCheckpoint.restore` 会比对 `sha256`，`checkpoints.py:112-120`）。
审计结论须写明依据的是记录还是校验。

## 8. 非目标（YAGNI）

以下不在本架构内，除非出现具体需求：

## 9. 未决事项

阶段 2 的准入条件已集中列于 §6.4，此处只记尚未定稿的内容。

### 9.1 未接入方法的选模需求

22 个方法中尚未接入者，是否有非常规选模需求（例如需要模型内部状态、或多输出），
须在接入时逐个确认；若有，不得默认其适配 L1 架构，**也不得默认 §6.2 的滚动选择对它成立**。

### 9.2 L2 的核算与跨批次留存

当前估算基于 ResNet-18 单组件；Self-PU 双 teacher、以及未来 22 方法中的多组件方法
（Dist-PU 等）需按组件数重新核算。**跨批次保留期须与 §5 的预算表一并定稿** ——
L2 一经删除，该 run 的模型级复核不可再恢复（训练的非确定性使「重跑即得同一权重」不成立），
因此这是由预算驱动、有代价的决策，不得默认「永久」。

### 9.3 L1 的落盘位置与形状

每 run 一个 npz、还是按批次合并；须与 manifest 的引用方式一并定稿。
